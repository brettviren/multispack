Distribution-independent scientific software

multispack.

Build a Spack software stack once, in a captured container, so its binaries run unmodified across a decade of Linux distributions — and prove it.

glibc 2.28 floor · manylinux_2_28 AlmaLinux 8/9/10 · Debian 12/13 · SLES 15 containers + podman $ORIGIN-relocatable SBOM + audited
The problem

One distribution, one uncaptured build

The current DUNE paradigm builds Spack packages for AlmaLinux 9 only, using the native host environment. That couples the software to two things it shouldn't depend on.

Problem 1

The build environment is not captured

A native, un-containerized build is hard to reproduce and drifts with the host. There is no pinned, digest-recorded record of exactly what produced the binaries.

Problem 2

The binaries are tied to one distribution

Built on AlmaLinux 9 (glibc 2.34), the binaries acquire GLIBC_2.34 symbols and will not run on anything older — AlmaLinux 8, EL7, older SLES on DOE HPC nodes. They also link the OS's own libraries, so a distribution's next major rebase can break them.

The concept

Build low, ship high, target the oldest glibc

multispack implements “Strategy B”: build inside a pinned container whose glibc is the oldest you must support, build everything above libc with Spack, and let glibc's forward symbol-versioning guarantee carry the binaries to every newer system.

The one-sentence pitch: glibc 2.28 is the manylinux_2_28 baseline — “these binaries have the same portability guarantee as a pip wheel,” backed by the entire Python packaging ecosystem. It is also newer than the glibc 2.17 that Fermilab shipped on SL7 until recently.

Why the direction matters

glibc never removes a symbol version, so a binary built against an older glibc runs on every newer one — but not the reverse. Building on AlmaLinux 9 bakes in GLIBC_2.34 and excludes AlmaLinux 8. Building on AlmaLinux 8 runs on 8, 9 and 10. This is measured, not asserted — see the pthread symbol-version demonstration.

How it works

The multispack.sh pipeline

One orchestrator drives every phase inside podman containers on three volumes (the /cvmfs install tree, a source+binary cache, and scratch). Each phase records JSON to meta/ for a self-contained HTML report.

volumes→ images→ bootstrap→ compiler→ compiler-validate→ concretize→ stack→ originize→ audit→ buildcache→ deploy→ validate→ report

Blue steps are fast gates — run them before committing to a multi-hour build. ./multispack.sh all runs the lot.

Set up

volumes · images

Create the podman volumes; build the pinned builder image (glibc-floor base) and the bare + -devel validator images for every target distro.

Toolchain

bootstrap · compiler · compiler-validate

Clone Spack; build the GCC ladder (base gcc 8.5 → gcc@14 → gcc@15) with its own binutils; then prove that gcc@15 runs and compiles in every bare validator.

Build

concretize · stack

Solve the environment (the fast gate where mistakes surface), then install the payload against the portable compiler on a generic x86_64_v3 microarchitecture.

Relocate & verify

originize · audit

Rewrite absolute RPATHs to store-relative $ORIGIN so the whole tree relocates as a unit; then ELF-audit the glibc symbol floor and confirm the only external library tier is libc.

Distribute

buildcache · deploy

Push the tree to a binary cache (so rebuilds and patches are cheap), and write per-flavour env.sh plus a deployment manifest.

Validate

validate

Run the payload in bare containers for every distribution, /cvmfs mounted read-only, nothing installed — if it runs, the $ORIGIN rpaths are carrying the load.

Custom stacks

makenv

Concretize + install any user spack.yaml into the shared tree — as a directory environment or a named managed environment — with pre-flight gates that fail fast when the container lacks a required OS-level dependency.

Security

sbom

Emit a CycloneDX/SPDX bill of materials from the lockfile and flag the CVE-prone leaves (openssl, curl, libxml2…) — ready for grype/trivy.

Utility

report · status · shell

Merge the phase JSON into report.html, summarize progress, or drop into a builder shell with the volumes mounted — where debugging happens.

The techniques that make it work

  • Flat install projection ({name}-{version}-{hash}): every prefix is a sibling, so store-relative rpaths are uniform and the distro/compiler never appear in a path.
  • In-place $ORIGIN rewriting that preserves hardlinks and shrinks-only, with padded install prefixes so a tree can later be relocated to a shorter path.
  • ELF audit that reports the glibc floor, unresolved DT_NEEDED, and every library the host must provide — turning “is this portable?” into a checkable property.
  • Cross-distribution validation matrix as a first-class artifact, including a deliberate musl xfail that marks the exact boundary of the approach.
Compared to the AL9-native paradigm

What it solves, what it adds, what it unlocks

Problems solved

  • One build runs on AlmaLinux 8/9/10, Debian 12/13, SLES 15 — including older DOE HPC nodes.
  • The build environment is captured: a digest-pinned image and a recorded lockfile / manifest.
  • Dodges the glibc 2.34 pthread cliff by building on the oldest glibc.
  • Immune to a distribution's library rebase — it ships its own libstdc++, boost, python, openssl…
  • Relocatable beyond /cvmfs: the tree moves as a unit via $ORIGIN.
  • Portability is audited and validated, not hoped for.

Problems it adds

  • Security patching of shipped libraries moves out of OS procedures — mitigated by sbom + a rebuild-and-redeploy process (bump the leaf, buildcache reuses the rest).
  • More moving parts: containers, podman, relocation, an ISA floor.
  • Larger footprint: shipping everything above libc costs disk (cheap on cached /cvmfs).
  • Runtime pitfalls it does not auto-solve — e.g. the static-TLS-surplus limit for dlopen-heavy plugin hosts (demonstrated here).
  • x86_64_v3 excludes pre-Haswell / pre-Zen CPUs; musl is out of scope by design.

Benefits unlocked

  • Multi-distribution CI: a green validation matrix is a stronger argument than any design document.
  • A precise per-artifact SBOM makes CVE detection continuous and exact.
  • DOE HPC facility access (the SLES 15 row) without a distro-specific rebuild.
  • A binary buildcache → fast patches and reproducible re-deploys.
  • An evidence-based criticism-response test suite that answers objections with runnable proof.

The next decade

When AlmaLinux 8 is the new Scientific Linux 7

The glibc floor is a knob, not a fixed choice. Everything in multispack is parameterized by BUILDER_BASE; the framework does not care which glibc is the oldest, only that it builds against it and proves the result. That is what lets the concept age gracefully.

Now — glibc 2.28 floor

AlmaLinux 8 / manylinux_2_28. Single ISA stream (x86_64_v3). Directory and managed environments, SBOMs, a cross-distro validation matrix, an evidence test suite.

Advance the floor as the community does

When AlmaLinux 8 is retired, re-point BUILDER_BASE to the new oldest supported base (manylinux_2_34, then _2_39, …) and rebuild. The validation matrix proves the new floor before anyone depends on it — floor migration becomes a routine, evidenced operation rather than a leap of faith.

Concurrent floors & ISA streams

Maintain two or three glibc-floor streams at once (exactly as manylinux ships multiple baselines), plus x86_64_v2/v3/v4 and aarch64 trees selected at runtime by archspec. One payload, several portability envelopes, chosen per node.

Strategy A escape hatch

When even the oldest reasonable glibc is too new for a target, ship our own glibc and dynamic loader (the EESSI compatibility-layer idea). The relocation machinery here — flat store, $ORIGIN, padded prefixes — is already a step toward that, needing only a fixed prefix and an own-loader PT_INTERP.

Security & provenance as automation

sbom → continuous grype/trivy scanning in CI; a rebuild-on-CVE path with a stated SLA for network-facing leaves; signed buildcaches and SLSA-style provenance so a deployed tree can be verified, not just trusted.

Distribution at scale

OCI-registry buildcaches, CVMFS publishing, and cross-facility binary sharing — so a stack built once is pulled everywhere as signed binaries, and a security patch propagates as fast as a registry sync.

The throughline: a scientific software release should be defined by what it is — a captured, audited, relocatable set of binaries with a bill of materials — not by which host happened to build it. multispack makes that definition executable, and keeps it true as the ground shifts underneath.
